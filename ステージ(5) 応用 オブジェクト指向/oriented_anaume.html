問1：クラスの基礎とインスタンス化

株式会社バンガード・ロジスティクスは、国内全域のサプライチェーンを牽引する総合物流企業であり、昨今の厳格なサービスレベルアグリーメント（SLA）の遵守を徹底するため、新たな配送時間監査システム「V-Track」の要件定義を行っている。このシステムの中核となるのが、各営業所に配備された配送車両の遅延状況を集約し、損害賠償額の引当金を自動計算するモジュールである。

本モジュールにおいて、各積荷を表す Cargo クラスは、荷主との契約によって厳密に定められた規定配送時間（targetHours: 整数型）と、GPSトラッキングから算出された実際の配送時間（actualHours: 整数型）を内部状態として保持する。一方、配送車両を表す Vehicle クラスは、自身が積み込んだ複数の Cargo インスタンスを配列 cargos としてカプセル化して保持する設計となっている。

監査規定によれば、Vehicle クラスの集約メソッド calcTotalDelayPenalty は、自身の持つすべての Cargo をループ走査し、actualHours が targetHours を超過している積荷を発見した場合、その「超過した時間（1時間単位）」に対し、一律で法定違約金レートである500円を乗じてペナルティ額を算出し、車両全体の総遅延損害金として合算・返却しなければならない。

  • cargos[1]： targetHours = 10, actualHours = 10
  • cargos[2]： targetHours = 15, actualHours = 17
  • cargos[3]： targetHours = 8, actualHours = 12
クラス Cargo private: 整数型: targetHours 整数型: actualHours public: Cargo(整数型: initTarget, 整数型: initActual) targetHours ← initTarget actualHours ← initActual getTargetHours(): 整数型 return targetHours getActualHours(): 整数型 return actualHours クラス Vehicle private: Cargoの配列: cargos public: Vehicle(Cargoの配列: initCargos) cargos ← initCargos calcTotalDelayPenalty(): 整数型 整数型: totalPenalty ← 0 整数型: i 整数型: excess for (i を 1 から cargosの要素数 まで 1 ずつ増やす) if (cargos[i].getActualHours() ＞ cargos[i].getTargetHours()) excess ← cargos[i].getActualHours() - cargos[i].getTargetHours() totalPenalty ← totalPenalty + (excess × 500) endif endfor return totalPenalty

設問

上記の Cargo インスタンス3つを要素として持つ配列を引数にして Vehicle クラスのインスタンスを生成した。この Vehicle インスタンスに対して calcTotalDelayPenalty() メソッドを呼び出したとき、メソッドの戻り値として正しいものはどれか。

  • ア： 0
  • イ： 500
  • ウ： 1000
  • エ： 1500
  • オ： 2000
  • カ： 2500
  • キ： 3000
  • ク： 3500

正解：キ

メソッド calcTotalDelayPenalty() のループ実行のトレースは以下の通りである。

【初期状態】totalPenalty = 0
【1回目のループ (i = 1)】
cargos[1] の getActualHours() は 10、getTargetHours() は 10。
`10 ＞ 10` は false となるため、if文の中身は実行されない。totalPenalty = 0。
【2回目のループ (i = 2)】
cargos[2] の getActualHours() は 17、getTargetHours() は 15。
`17 ＞ 15` は true となるため、if文が実行される。
excess ← 17 - 15 = 2。
totalPenalty ← 0 + (2 × 500) = 1000。
【3回目のループ (i = 3)】
cargos[3] の getActualHours() は 12、getTargetHours() は 8。
`12 ＞ 8` は true となるため、if文が実行される。
excess ← 12 - 8 = 4。
totalPenalty ← 1000 + (4 × 500) = 1000 + 2000 = 3000。

すべての走査が終了し、戻り値は 3000 となる。したがって正解は「キ」である。

問2：継承とオーバーライド

株式会社セキュアクラウド統括部門では、次世代のIaaS環境において各テナントに割り当てられるサーバーの月額利用料を算出する課金クラス群を再設計している。基本となる BaseServer クラスは、インスタンス変数として baseRate (1日あたりの基本単価) と activeDays (当月の稼働日数) をカプセル化して持ち、これらを乗算して基本利用料を算出する calcMonthlyFee メソッドを備えている。

今回、国家機密レベルの通信を取り扱う顧客向けに、新たに暗号化処理用ハードウェアモジュールを搭載した SecureServer クラスを、BaseServer クラスを継承して定義することとなった。SecureServer は独自の追加インスタンス変数として cryptoKeyCount (払い出された暗号キーの数) を保持する。

課金仕様書によれば、SecureServer の calcMonthlyFee メソッドはオーバーライドされ、「親クラスが本来算出する基本利用料」に対し、「cryptoKeyCount に1000円を乗じたセキュリティ加算額」を合算した金額を返さなければならない。カプセル化の原則に従い、親クラスの private 変数には直接アクセスせず、適切なメソッド呼び出しを行う必要がある。

クラス BaseServer private: 整数型: baseRate 整数型: activeDays public: BaseServer(整数型: initRate, 整数型: initDays) baseRate ← initRate activeDays ← initDays calcMonthlyFee(): 整数型 return baseRate × activeDays クラス SecureServer extends BaseServer private: 整数型: cryptoKeyCount public: SecureServer(整数型: initRate, 整数型: initDays, 整数型: initKeys) super(initRate, initDays) /* 親クラスのコンストラクタ呼び出し */ cryptoKeyCount ← initKeys calcMonthlyFee(): 整数型 /* 親クラスの基本利用料に、暗号キー数×1000を加算して返す */ return [ a ]

設問

プログラム中の空欄 [ a ] に入る最も適切な処理はどれか。

  • ア： this.calcMonthlyFee() + (cryptoKeyCount × 1000)
  • イ： BaseServer.calcMonthlyFee() + (cryptoKeyCount × 1000)
  • ウ： super.baseRate × activeDays + (cryptoKeyCount × 1000)
  • エ： super.calcMonthlyFee() + (cryptoKeyCount × 1000)
  • オ： calcMonthlyFee() + (cryptoKeyCount × 1000)
  • カ： super() + (cryptoKeyCount × 1000)
  • キ： super.calcMonthlyFee + (cryptoKeyCount × 1000)
  • ク： baseRate × activeDays + cryptoKeyCount × 1000

正解：エ

この問題は継承における親クラスのメソッド呼び出し構文とカプセル化の理解を問うものである。

SecureServer は BaseServer を継承（extends）している。SecureServer 内でオーバーライドされた calcMonthlyFee メソッドから、親クラスの元々の calcMonthlyFee を呼び出すには super.calcMonthlyFee() を使用しなければならない。

「ア」や「オ」は自身の calcMonthlyFee を再帰的に呼び出すことになり、無限ループ（スタックオーバーフロー）を引き起こす。「イ」は静的メソッド（クラスメソッド）の呼び出し構文であり不適切。「ウ」や「ク」は親クラスの baseRate や activeDays が private で宣言されているため、子クラスから直接アクセスできずコンパイルエラーとなる。「カ」の super() は親クラスのコンストラクタ呼び出しに限定される。「キ」は括弧がないためメソッド呼び出しにならない。

したがって、正しく親メソッドを実行して加算額を足し合わせる「エ」が正解となる。

問3：多態性（ポリモーフィズム）

多国籍IT企業のグローバル人事部では、全従業員向けに新たな福利厚生プラットフォーム「Benefit-Core」を導入した。このシステムでは、各従業員が申請した経費（経費精算額）に応じて、社内ポイント（RewardPoints）を還元する処理を実行する。システムは共通インタフェース BenefitPlan を定義しており、このインタフェースは processClaim(整数型: amount) メソッドおよび getPoints() メソッドの契約を強制する。

一般社員向けの StandardPlan クラスは、申請額の10%（端数切り捨て）を現在の points に加算する。一方で、上級管理職向けに発行される ExecutivePlan クラスは、申請額の20%（端数切り捨て）を算出した後、さらに固定の特別ボーナスとして500ポイントを上乗せして points に加算する極めて優遇された仕様となっている。どちらのクラスも BenefitPlan インタフェースを実装しており、呼び出し側はオブジェクトの実際の型を意識することなく、ポリモーフィズムを利用して一括で処理を委譲できる。

システム管理者オブジェクトは、従業員が保有する複数のプラン（BenefitPlan の配列）と、それぞれの申請額（配列）を受け取り、ループ処理によってすべての申請を一斉に確定させたのち、全プランの最終的な合計ポイントを算出して返す calcAllPoints メソッドを実行する。

設問

以下のインスタンスと引数で calcAllPoints メソッドを呼び出した時、戻り値として返される値はどれか。

plans = [new StandardPlan(100), new ExecutivePlan(50), new StandardPlan(200)]
claimAmounts = [3000, 4000, 1500]

  • ア： 1200
  • イ： 1600
  • ウ： 1750
  • エ： 1850
  • オ： 2000
  • カ： 2100
  • キ： 2400
  • ク： 2650

正解：カ

ポリモーフィズムにより、plans[i].processClaim() は各インスタンスの実体（クラス）に定義されたメソッドを動的に呼び出す。

【ループ1回目：i = 1】

対象：StandardPlan (初期points = 200), amount = 1500

すべての処理が完了し、最終的な total の値は 2100 となる。したがって正解は「カ」。

問4：再帰関数

巨大な物流倉庫群の全容を管理するWMS（倉庫管理システム）において、再帰関数を用いた総在庫数の算出モジュールが稼働している。この倉庫はマトリックス状の複雑な階層構造を形成しており、論理的な保管単位は StorageNode クラスとして定義されている。

各 StorageNode インスタンスは、その保管区画（ノード）自身に直置きされている品物の数（directItems）を持つと同時に、内部にさらに細分化された子区画群を保持するための配列（childNodes: StorageNode の配列）をカプセル化している。システム仕様上、在庫集計を行う再帰関数 calcTotalInventory は、引数として渡された StorageNode の直置き品目数に加えて、すべての childNodes に対する同関数の戻り値を再帰的に合算し、ツリー全体の総アイテム数を返すよう実装されている。

監査担当者は、特定の区画群に対してこの集計ロジックを手動でトレースし、論理破綻がないか検証するよう指示を出した。深層までネストされたインスタンス群に対し、正しく再帰呼び出しが行われた場合の最終的な総数を導き出せ。

以下のツリー構造を持つ rootNode を引数として calcTotalInventory(rootNode) を呼び出した場合、戻り値はどれか。

再帰関数 calcTotalInventory は、親ノードの directItems と、すべての子ノードの calcTotalInventory の結果を足し合わせる。

calcTotalInventory(NodeA2) = 8 (子なし)

再帰呼び出しがすべて完了した時点での最終的な戻り値は 60 となる。正解は「カ」。

問5：オブジェクトの参照渡しによる副作用

超高速アルゴリズムトレードをエミュレートする株式取引シミュレーションシステムにおいて、並行稼働する複数の取引エージェント（Agent）が、メモリ上の単一の共有リソースである銘柄インスタンス（Stock）の参照を保持し、先着順で買い注文を処理している。

システム設計上、Stock クラスは市場に流通している発行済残株数（remainingShares）を中央管理している。各 Agent はコンストラクタで渡された Stock のインスタンスを自身のメンバ変数 targetStock に代入することで、全員が「全く同じ実体」を指し示すエイリアス（別名参照）状態を形成している。

Agent クラスの executeBuy(整数型: orderVolume) メソッドは、自身の購入済み株数（purchasedShares）に株を追加する際、まず共有されている Stock 側の残株数が注文数以上あるかを確認する。十分な残数があれば、参照元である Stock の残数を減算し、自身の purchasedShares に注文数を加算して true を返す。もし残数が不足していれば、部分的な買い付けは行わずに false を返し終了する。

このシビアなリソース競合環境において、特定の順序で注文が発火した際に引き起こされる状態変化（副作用）を追跡せよ。

クラス Stock public: 整数型: remainingShares public: Stock(整数型: initShares) remainingShares ← initShares getRemainingShares(): 整数型 return remainingShares reduceShares(整数型: amount) remainingShares ← remainingShares - amount クラス Agent private: Stock: targetStock 整数型: purchasedShares ← 0 public: Agent(Stock: stockRef) targetStock ← stockRef executeBuy(整数型: orderVolume): 論理型 if (targetStock.getRemainingShares() ≧ orderVolume) /* 共有リソースの株数を減らす（副作用が発生） */ targetStock.reduceShares(orderVolume) purchasedShares ← purchasedShares + orderVolume return true else return false endif getPurchasedShares(): 整数型 return purchasedShares

設問

以下の一連の処理が順次実行された直後において、sharedStock の remainingShares の値と、agent2 の getPurchasedShares() の戻り値の組み合わせとして正しいものはどれか。

Stock: sharedStock ← new Stock(1000)
Agent: agent1 ← new Agent(sharedStock)
Agent: agent2 ← new Agent(sharedStock)
Agent: agent3 ← new Agent(sharedStock)

agent1.executeBuy(400)
agent2.executeBuy(700)
agent3.executeBuy(500)
  • ア： (100, 0)
  • イ： (100, 700)
  • ウ： (600, 0)
  • エ： (0, 0)
  • オ： (500, 0)
  • カ： (100, 600)
  • キ： (600, 700)
  • ク： (0, 700)

正解：ア

すべての Agent インスタンスが単一の Stock インスタンス (sharedStock) を参照渡しで共有しているため、1つのエージェントの操作が他のエージェントの判定に直ちに影響を及ぼす（副作用）。

【初期状態】
sharedStock の remainingShares = 1000
全Agent の purchasedShares = 0

【agent1.executeBuy(400) の実行】
remainingShares(1000) ≧ 400 は true。
sharedStock の remainingShares は 1000 - 400 = 600 になる。
agent1 の purchasedShares は 400 になる。

【agent2.executeBuy(700) の実行】
remainingShares(600) ≧ 700 は false。条件を満たさず false が返る。
sharedStock の残数は 600 のまま。
agent2 の purchasedShares は 0 のままである。

【agent3.executeBuy(500) の実行】
remainingShares(600) ≧ 500 は true。
sharedStock の remainingShares は 600 - 500 = 100 になる。
agent3 の purchasedShares は 500 になる。

最終的に sharedStock の remainingShares は 100、agent2 の購入数は 0 であるため、組み合わせは (100, 0) となる。したがって正解は「ア」。

問6：リスト構造とオブジェクト操作の応用

次世代ネットワーク機器のトラフィック制御機構において、受信したデータパケット（Packet クラス）の処理キューを巡回・フィルタリングする高度なアルゴリズムを実装している。このルーターは、ノイズが混入したパケットを即座に破棄せず、後続のリカバリプロセスで復元を試みるためのフォールトトレラント設計を採用している。

手続 processPacketQueue は、パケットの配列である packetQueue と、配列内の有効な先頭要素を示すポインタ head、および有効な末尾要素を示すポインタ tail を引数に取る。処理ループ内では、キューの先頭からパケットを一つ取り出し（デキュー操作）、そのパケットの errorRate (エラー率) が規定値 threshold 以下であれば正常として routePacket に渡し転送する。

しかし、errorRate が規定値を超えていた場合、そのパケットは転送されず、再送待機用として「現在のキューの最後尾に再度追加」されなければならない（巡回処理）。この再配置ロジックにおいて、キューの末尾ポインタを正しくインクリメントし、配列の最後尾にオブジェクトの参照を格納する操作が求められる。なお、配列のインデックスは1から始まり、配列の容量は無限に拡張可能であると仮定する。

手続: processPacketQueue(Packetの配列: packetQueue, 整数型: head, 整数型: tail, 整数型: threshold) Packet: currentPacket while (head ≦ tail) /* 先頭からパケットを取り出す */ currentPacket ← packetQueue[head] head ← head + 1 if (currentPacket.getErrorRate() ≦ threshold) /* 正常パケットはルーティング処理へ */ routePacket(currentPacket) else /* エラーパケットを配列の最後尾に追加して巡回させる */ [ a ] endif endwhile

設問

プログラム中の空欄 [ a ] に入る最も適切な処理を選択せよ。処理は複数行にわたる場合がある。

  • ア：
    tail ← tail + 1
    packetQueue[tail] ← currentPacket
  • イ：
    packetQueue[head] ← currentPacket
    head ← head + 1
  • ウ：
    tail ← tail - 1
    packetQueue[tail] ← currentPacket
  • エ：
    packetQueue[tail + 1] ← currentPacket
    head ← tail
  • オ：
    currentPacket ← packetQueue[tail]
    tail ← tail + 1
  • カ：
    packetQueue[tail] ← currentPacket
    tail ← tail - 1
  • キ：
    head ← head + 1
    packetQueue[tail] ← currentPacket
  • ク：
    packetQueue[1] ← currentPacket
    tail ← tail + 1

正解：ア

キュー（待ち行列）から取り出した要素を再度キューの末尾（最後尾）に追加するエンキュー処理の基本ロジックである。

変数 tail は現在の配列における「有効なデータの末尾インデックス」を指している。
新たな要素を末尾に追加するためには、まず末尾ポインタ tail の値を 1 つ増やして（インクリメント）拡張し、その新しい tail の位置が示す配列要素 packetQueue[tail] に対して対象の currentPacket を代入しなければならない。

「イ」は先頭側に上書きしてしまっているため巡回にならない。「ウ」や「カ」はポインタを減算しており、既存のデータを破壊してしまう。「エ」は代入までは良いが、先頭ポインタ head を末尾にジャンプさせてしまうためループが即座に崩壊する。「オ」は代入の向きが逆（配列から変数へ）である。

したがって、正しい順序で末尾への追加操作を行っている「ア」が正解となる。
