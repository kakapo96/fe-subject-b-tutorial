問1：線形探索（番兵法と条件付き走査）

貴様らのようなひよっこエンジニアが最初に直面する壁、それが配列の境界管理だ！甘ったれるな！
社内の入退室管理システムにおいて、特定の物理キーカードID（targetId）がアクセスログ（empIds）内に存在するかを判定し、存在すればそのインデックスを返す関数 searchEmployeeId を作成する。
ただし、無能なプログラマが書きがちな「ループのたびに配列の終端に達したか判定する」無駄な処理を省くため、配列の末尾に探したい値を意図的に追加する「番兵法」を採用している。この泥臭いロジックを読み解き、空欄を埋めろ！

  • empIds：従業員のキーカードIDが格納された整数型の配列（インデックスは1から開始）
  • targetId：探索対象のキーカードID
  • totalCount：本来のアクセスログの件数（番兵を追加する前の要素数）
○整数型: searchEmployeeId(整数型の配列: empIds, 整数型: targetId) 整数型: currentIndex ← 1 整数型: totalCount ← empIds の要素数 /* 配列の末尾に番兵をセット */ empIds[totalCount + 1] ← targetId while (empIds[currentIndex] ≠ targetId) currentIndex ← [ a ] endwhile /* インデックスが元の要素数以内なら発見、超えていれば番兵 */ if (currentIndex [ b ] totalCount) return currentIndex else return -1 endif

設問

プログラム中の空欄 [ a ] および [ b ] に入れる適切な字句の組み合わせを、ア〜クの中から選べ。

  • ア： [ a ] currentIndex + 1 , [ b ] ≦
  • イ： [ a ] currentIndex + 1 , [ b ] ＜
  • ウ： [ a ] currentIndex + 1 , [ b ] =
  • エ： [ a ] currentIndex , [ b ] ≦
  • オ： [ a ] currentIndex , [ b ] ＜
  • カ： [ a ] currentIndex - 1 , [ b ] ≦
  • キ： [ a ] currentIndex + 2 , [ b ] =
  • ク： [ a ] currentIndex + 2 , [ b ] ≦

正解：ア

この程度の番兵法でつまずくようならエンジニアを辞めろ！
【aの解説】whileループ内では、現在のインデックスの要素が探索値と一致しない限り、次の要素へ進む必要がある。したがって currentIndex ← currentIndex + 1 が絶対の正解だ。ここでインデックスを減らしたり維持したりする選択肢を選ぶ奴は論外だ。
【bの解説】ループを抜けた時、currentIndex が「番兵として追加した位置（totalCount + 1）」であれば、元々の配列には存在しなかったことを意味する。逆に、totalCount 以下であれば本来のデータ群の中で発見したことになる。よって ≦ が正解となる。「＜」では、配列の最後尾（要素数ぴったりの位置）で発見した場合にエラー扱いになってしまうぞ！

問2：2分探索（バイナリサーチと境界管理）

ただの2分探索だと思ったら大間違いだ！インデックスの境界管理すらできずにシステムを落とす気か！
この関数 findInsertPosition は、昇順にソートされた商品価格の履歴データ（priceList）に対して、新たな価格（newPrice）を「昇順を維持したまま追加する場合、どの位置（インデックス）に挿入すべきか」を特定するためのものである。
完全に一致する値が存在しなくてもエラーを返すのではなく、境界（Lower Bound）を見極めて最終的な挿入位置を割り出さねばならない。パニックにならず、1ループごとの leftIndex と rightIndex の交差を泥臭くトレースしろ！

  • priceList：昇順に整列済みの整数型の配列
  • newPrice：新たに挿入したい価格データ
  • ※配列内に newPrice と同じ値が複数存在する場合、最初に出現する位置を返す仕様とする。
○整数型: findInsertPosition(整数型の配列: priceList, 整数型: newPrice) 整数型: leftIndex ← 1 整数型: rightIndex ← priceList の要素数 整数型: midIndex while (leftIndex [ a ] rightIndex) midIndex ← (leftIndex + rightIndex) ÷ 2 の商 if (priceList[midIndex] [ b ] newPrice) /* 一致しても打ち切らず、さらに左側を探索して最初に出現する位置を探す */ rightIndex ← midIndex - 1 else leftIndex ← midIndex + 1 endif endwhile /* 最終的な挿入位置を返す */ return [ c ]

設問

プログラム中の空欄 [ a ] 〜 [ c ] に入れる適切な字句の組み合わせを、ア〜クの中から選べ。

  • ア： [ a ] ≦ , [ b ] ≧ , [ c ] leftIndex
  • イ： [ a ] ≦ , [ b ] ＞ , [ c ] rightIndex
  • ウ： [ a ] ＜ , [ b ] ≧ , [ c ] leftIndex
  • エ： [ a ] ＜ , [ b ] ＞ , [ c ] rightIndex
  • オ： [ a ] ≦ , [ b ] = , [ c ] leftIndex
  • カ： [ a ] ≦ , [ b ] ≦ , [ c ] midIndex
  • キ： [ a ] ＜ , [ b ] ≦ , [ c ] midIndex
  • ク： [ a ] = , [ b ] ≧ , [ c ] rightIndex

正解：ア

手計算の労力を惜しむ奴から足元をすくわれる！
【aの解説】通常の2分探索と同様、探索範囲が1要素になった時（leftIndex = rightIndex）もチェックを行う必要があるため、≦ が正解となる。「＜」にしてしまうと、最後の1要素の確認が漏れるぞ！
【bの解説】「同じ値があれば一番左（Lower Bound）」を見つけるため、priceList[midIndex] が newPrice と「等しい」場合も rightIndex ← midIndex - 1 として左半分の探索を続行する必要がある。よって ≧ が正解だ。
【cの解説】ループ終了時、leftIndex と rightIndex は交差している。newPrice より小さい要素はすべて leftIndex の左側に寄り、newPrice 以上の要素はすべて leftIndex 以降に追いやられる。したがって、挿入すべき正しいインデックスは leftIndex となる。

問3：バブルソート（隣接交換法と最適化）

レガシーな銀行のメインフレームで、日次の決済バッチ処理を動かすことを想像しろ！無駄な自己ループは命取りだ。
この関数 optimizeTransactionSort は、毎日の取引金額データ（transAmounts）を昇順にソートするバブルソートである。ただし、既に整列済みのデータを無駄に走査し続けないよう、「1回もスワップ（交換）が発生しなかったら即座に処理を終了する」という最適化フラグが組み込まれている。
外側と内側のループ境界、そして一時変数を使ったスワップのセオリーを完璧に理解していなければ、このコードは完成しないぞ！

  • transAmounts：日次の決済金額が格納された整数型の配列
  • isSwapped：その周回で一度でも交換処理が行われたかを記録する論理型のフラグ
  • ※配列は1から始まり、昇順（小さい順）に整列させる。
○手続: optimizeTransactionSort(整数型の配列: transAmounts) 整数型: loopCounter, compareIndex, tempValue 整数型: arrayLength ← transAmounts の要素数 論理型: isSwapped for (loopCounter を 1 から arrayLength - 1 まで 1 ずつ増やす) isSwapped ← false for (compareIndex を 1 から [ a ] まで 1 ずつ増やす) if (transAmounts[compareIndex] ＞ transAmounts[compareIndex + 1]) tempValue ← transAmounts[compareIndex] transAmounts[compareIndex] ← transAmounts[compareIndex + 1] transAmounts[compareIndex + 1] ← [ b ] isSwapped ← [ c ] endif endfor /* 交換が一度も発生しなければ整列完了とみなす */ if (isSwapped = false) return endif endfor

設問

プログラム中の空欄 [ a ] 〜 [ c ] に入れる適切な字句の組み合わせを、ア〜クの中から選べ。

  • ア： [ a ] arrayLength - loopCounter , [ b ] tempValue , [ c ] true
  • イ： [ a ] arrayLength - loopCounter , [ b ] transAmounts[compareIndex] , [ c ] true
  • ウ： [ a ] arrayLength - loopCounter , [ b ] tempValue , [ c ] false
  • エ： [ a ] arrayLength , [ b ] tempValue , [ c ] true
  • オ： [ a ] arrayLength , [ b ] transAmounts[compareIndex] , [ c ] false
  • カ： [ a ] loopCounter , [ b ] tempValue , [ c ] true
  • キ： [ a ] arrayLength - loopCounter - 1 , [ b ] tempValue , [ c ] true
  • ク： [ a ] arrayLength - 1 , [ b ] transAmounts[compareIndex + 1] , [ c ] false

正解：ア

配列の範囲外参照エラーで夜間バッチを落としたら誰が責任を取るんだ！
【aの解説】バブルソートの外側ループが loopCounter 回進むごとに、配列の後方には loopCounter 個の最大値が確定して並んでいく。したがって内側ループで比較すべき上限は arrayLength - loopCounter となる。これを arrayLength のままにすると compareIndex + 1 で確実に配列外参照を起こしてシステムが死ぬ！
【bの解説】スワップ処理の基本である。tempValue に退避した元の transAmounts[compareIndex] の値を、右側の要素に代入し直すため tempValue が入る。
【cの解説】交換処理が発生したのだから、当然 isSwapped は true に更新されなければならない。

問4：選択ソート（基本選択法とスワップ判定）

データベースのクエリ実行時間（ミリ秒）をソートし、ロック遅延のボトルネックを特定する任務だ！
関数 sortResponseTimes は選択ソートを用いて respTimes を昇順に並べ替えるが、今回はSSDへの無駄な書き込みを減らすため、「最小値が既に正しい位置にある場合は、配列の書き換え（スワップ）をスキップする」という条件分岐が追加されている。
内側ループのインデックスの開始位置と、スワップ直前の条件式の意味を的確に読み取れるか試してやる！

  • respTimes：DBクエリの実行時間（ミリ秒）が格納された整数型の配列
  • minTimeIdx：未整列部分の中で最小の値を持つ要素のインデックスを保持する変数
○手続: sortResponseTimes(整数型の配列: respTimes) 整数型: outerIdx, innerIdx, minTimeIdx, tempTime 整数型: totalLogs ← respTimes の要素数 for (outerIdx を 1 から totalLogs - 1 まで 1 ずつ増やす) minTimeIdx ← outerIdx /* 未整列の範囲から最小値を探す */ for (innerIdx を [ a ] から totalLogs まで 1 ずつ増やす) if (respTimes[innerIdx] ＜ respTimes[minTimeIdx]) minTimeIdx ← [ b ] endif endfor /* 最小値が現在の位置と異なる場合のみ自己代入を省いてスワップ */ if (minTimeIdx [ c ] outerIdx) tempTime ← respTimes[outerIdx] respTimes[outerIdx] ← respTimes[minTimeIdx] respTimes[minTimeIdx] ← tempTime endif endfor

設問

プログラム中の空欄 [ a ] 〜 [ c ] に入れる適切な字句の組み合わせを、ア〜クの中から選べ。

  • ア： [ a ] outerIdx + 1 , [ b ] innerIdx , [ c ] ≠
  • イ： [ a ] outerIdx + 1 , [ b ] minTimeIdx , [ c ] ≠
  • ウ： [ a ] outerIdx , [ b ] innerIdx , [ c ] =
  • エ： [ a ] outerIdx , [ b ] minTimeIdx , [ c ] ≠
  • オ： [ a ] outerIdx + 1 , [ b ] innerIdx , [ c ] =
  • カ： [ a ] 1 , [ b ] innerIdx , [ c ] ≠
  • キ： [ a ] outerIdx + 1 , [ b ] minTimeIdx , [ c ] =
  • ク： [ a ] outerIdx - 1 , [ b ] innerIdx , [ c ] ≠

正解：ア

選択ソートの挙動を脳内で映像化できずにプロの現場で通用すると思うな！
【aの解説】外側ループの outerIdx の位置は自身を仮の最小値としているため、内側ループの比較は「その1つ右の要素」から最後まで行えばよい。よって outerIdx + 1 から始めるのが鉄則だ。
【bの解説】現在の最小値 respTimes[minTimeIdx] よりも小さい値を発見した場合、その時のインデックスである innerIdx を新たな最小値のインデックスとして記録しなければならない。
【cの解説】無駄な書き込みを防ぐ仕様である。見つかった最小値のインデックス minTimeIdx が、交換対象である現在の位置 outerIdx と「異なる（≠）」場合のみ、スワップ処理を実行するのだ。

問5：挿入ソート（基本挿入法と要素のシフト）

自動倉庫システムに次々と運ばれてくる巨大な物流クレート群を、総重量（packWeights）ベースで挿入ソートしていく処理だ。
すでに整列済みの範囲に対して、新たなクレートの重量 targetWeight を適切な位置に滑り込ませるため、それより重いクレート群を「1つ後ろへシフト（ずらす）」する泥臭いwhileループが組み込まれている。
変数の退避とインデックスの増減に惑わされず、配列の中身がどう押し出されていくか、頭に汗をかいてトレースしろ！

  • packWeights：クレートの重量が格納された整数型の配列（昇順に整列させる）
  • targetWeight：現在挿入位置を探しているクレートの重量（一時退避変数）
○手続: sortPackageWeights(整数型の配列: packWeights) 整数型: currentIdx, shiftIdx, targetWeight 整数型: maxPacks ← packWeights の要素数 for (currentIdx を 2 から maxPacks まで 1 ずつ増やす) targetWeight ← packWeights[currentIdx] shiftIdx ← currentIdx - 1 /* targetWeightより重いクレートを後ろへ1つずつずらす */ while (shiftIdx ＞ 0 [ a ] packWeights[shiftIdx] ＞ targetWeight) packWeights[shiftIdx + 1] ← [ b ] shiftIdx ← shiftIdx - 1 endwhile /* 空いた位置に退避しておいた重量を挿入する */ packWeights[shiftIdx + 1] ← [ c ] endfor

設問

プログラム中の空欄 [ a ] 〜 [ c ] に入れる適切な字句の組み合わせを、ア〜クの中から選べ。

  • ア： [ a ] and , [ b ] packWeights[shiftIdx] , [ c ] targetWeight
  • イ： [ a ] and , [ b ] packWeights[shiftIdx + 1] , [ c ] targetWeight
  • ウ： [ a ] and , [ b ] packWeights[shiftIdx] , [ c ] packWeights[currentIdx]
  • エ： [ a ] or , [ b ] packWeights[shiftIdx] , [ c ] targetWeight
  • オ： [ a ] or , [ b ] packWeights[shiftIdx + 1] , [ c ] packWeights[currentIdx]
  • カ： [ a ] and , [ b ] packWeights[shiftIdx - 1] , [ c ] targetWeight
  • キ： [ a ] or , [ b ] packWeights[shiftIdx - 1] , [ c ] packWeights[currentIdx]
  • ク： [ a ] and , [ b ] targetWeight , [ c ] packWeights[shiftIdx]

正解：ア

配列の要素を上書きしてデータを消失させるドジを踏むな！
【aの解説】配列の先頭を越えない（shiftIdx ＞ 0）という条件「かつ」、現在の要素が挿入対象より大きい（packWeights[shiftIdx] ＞ targetWeight）という2つの条件を同時に満たす間だけシフト処理を続けるため、論理演算子 and が入る。
【bの解説】要素を1つ後ろへずらすのだから、現在の要素 packWeights[shiftIdx] を、その1つ後ろの packWeights[shiftIdx + 1] に代入するのが正しいシフト処理である。
【cの解説】whileループを抜けた時点での shiftIdx + 1 が、最終的に確保された空きスペース（挿入位置）である。ここには、最初に退避しておいた targetWeight を代入しなければならない。元のインデックスである currentIdx は既に上書きされている可能性があるため使えないぞ！

問6：シェルソート（改良挿入法とギャップ縮小）

火星探査機から送られてくる大量のテレメトリパケット（telemetryData）を、メモリオーバーロードを防ぎながら高速に事前ソートするシェルソートだ！
要素間の一定のギャップ（gapSize）をあけて取り出した要素群に対して挿入ソートを行い、段階的にギャップを半減させていく。実質的な3重ループ構造になっており、インデックスのオフセット計算が少しでも狂えば配列は完全に崩壊する。
ギャップを意識した挿入ソートの境界値と、シフト処理の相対距離を正確に見極めろ！

  • telemetryData：テレメトリパケットデータが格納された整数型の配列
  • gapSize：比較対象となる要素間の間隔（ループのたびに半減する）
○手続: fastTelemetrySort(整数型の配列: telemetryData) 整数型: scanIdx, shiftIdx, gapSize, tempPacket 整数型: totalPackets ← telemetryData の要素数 gapSize ← totalPackets ÷ 2 の商 while (gapSize ＞ 0) for (scanIdx を [ a ] から totalPackets まで 1 ずつ増やす) tempPacket ← telemetryData[scanIdx] shiftIdx ← scanIdx - gapSize while (shiftIdx ＞ 0 and telemetryData[shiftIdx] ＞ tempPacket) telemetryData[[ b ]] ← telemetryData[shiftIdx] shiftIdx ← shiftIdx - gapSize endwhile telemetryData[[ b ]] ← tempPacket endfor gapSize ← [ c ] endwhile

設問

プログラム中の空欄 [ a ] 〜 [ c ] に入れる適切な字句の組み合わせを、ア〜クの中から選べ。

  • ア： [ a ] gapSize + 1 , [ b ] shiftIdx + gapSize , [ c ] gapSize ÷ 2 の商
  • イ： [ a ] gapSize + 1 , [ b ] shiftIdx - gapSize , [ c ] gapSize ÷ 2 の商
  • ウ： [ a ] gapSize , [ b ] shiftIdx + gapSize , [ c ] gapSize ÷ 2 の商
  • エ： [ a ] gapSize , [ b ] shiftIdx - gapSize , [ c ] gapSize - 1
  • オ： [ a ] gapSize + 1 , [ b ] shiftIdx + gapSize , [ c ] gapSize - 1
  • カ： [ a ] gapSize - 1 , [ b ] shiftIdx + gapSize , [ c ] gapSize ÷ 2 の商
  • キ： [ a ] 1 , [ b ] shiftIdx + 1 , [ c ] gapSize ÷ 2 の商
  • ク： [ a ] gapSize + 1 , [ b ] shiftIdx , [ c ] gapSize - 1

正解：ア

3重ループのオフセット計算にひるむな！気合で追いきれ！
【aの解説】通常の挿入ソートが 2（つまり 1 + 1）から始まるように、ギャップが gapSize のシェルソートの比較基準は gapSize + 1 から開始しなければならない。gapSize そのものから始めると、scanIdx - gapSize = 0 となり配列外参照を起こす。
【bの解説】要素をシフトする際、通常の挿入ソートでは shiftIdx + 1 だった場所が、シェルソートでは shiftIdx + gapSize 離れた位置への代入となる。
【cの解説】シェルソートのギャップは段階的に狭めていく。初期設定が totalPackets ÷ 2 の商 であったように、ループの最後で gapSize ← gapSize ÷ 2 の商 として半減させていくのが基本アルゴリズムの定石である。

問7：クイックソート（分割処理とポインタ交差）

マイクロ秒単位のティックログ（tradeLogs）を解析する高頻度取引システムだ！遅延は即座に莫大な損失に直結する。
この関数 partitionTradeLogs はクイックソートのコアとなる「分割処理（Hoareの分割方式）」を担っている。配列の中央にある値をピボット（pivotVolume）として選定し、左端からのポインタ leftPtr と右端からのポインタ rightPtr を内側へ進めながら、位置が不適切な要素を見つけ次第スワップする。
ポインタが交差する条件、そして無限ループに陥らないための不等号の厳格な設定を、限界の集中力で見極めろ！

  • tradeLogs：取引ボリュームが格納された整数型の配列
  • leftBound / rightBound：分割対象となる配列範囲の左端および右端のインデックス
  • pivotVolume：分割の基準となる値（今回は中央の要素を採用）
○整数型: partitionTradeLogs(整数型の配列: tradeLogs, 整数型: leftBound, 整数型: rightBound) 整数型: pivotVolume, leftPtr, rightPtr, tempLog pivotVolume ← tradeLogs[(leftBound + rightBound) ÷ 2 の商] leftPtr ← leftBound rightPtr ← rightBound while (true) /* ピボットより小さい要素はスキップして右へ進む */ while (tradeLogs[leftPtr] [ a ] pivotVolume) leftPtr ← leftPtr + 1 endwhile /* ピボットより大きい要素はスキップして左へ進む */ while (tradeLogs[rightPtr] [ b ] pivotVolume) rightPtr ← rightPtr - 1 endwhile /* ポインタが交差または重なったら分割完了 */ if (leftPtr [ c ] rightPtr) return rightPtr endif /* 不適切な位置にある要素同士をスワップ */ tempLog ← tradeLogs[leftPtr] tradeLogs[leftPtr] ← tradeLogs[rightPtr] tradeLogs[rightPtr] ← tempLog leftPtr ← leftPtr + 1 rightPtr ← rightPtr - 1 endwhile

設問

プログラム中の空欄 [ a ] 〜 [ c ] に入れる適切な字句の組み合わせを、ア〜クの中から選べ。

  • ア： [ a ] ＜ , [ b ] ＞ , [ c ] ≧
  • イ： [ a ] ≦ , [ b ] ＞ , [ c ] ≧
  • ウ： [ a ] ＜ , [ b ] ≧ , [ c ] ≧
  • エ： [ a ] ≦ , [ b ] ≧ , [ c ] ＞
  • オ： [ a ] ＜ , [ b ] ＞ , [ c ] ＞
  • カ： [ a ] ＞ , [ b ] ＜ , [ c ] ≧
  • キ： [ a ] ＞ , [ b ] ＜ , [ c ] ＞
  • ク： [ a ] ≦ , [ b ] ≧ , [ c ] ≧

正解：ア

ポインタの交差条件を見誤ればスタックオーバーフローでシステムが死ぬぞ！
【aの解説】左側からは「ピボットより小さい値」は正しい位置にあるためスキップする。したがって ＜ が入る。ここで ≦ を使うと、値がピボットと等しい場合にポインタが突き抜けて境界エラーを起こす危険がある。
【bの解説】右側からは「ピボットより大きい値」をスキップする。同様に ＞ が正解である。
【cの解説】両側からの探索が進み、左ポインタが右ポインタを通り越した、あるいは同じ位置で衝突した時点（leftPtr ≧ rightPtr）で、ピボットを境界とした左右の分割が完了したことになる。ここで単なる ＞ を使うと、同じ要素を指した際に無限ループに陥る恐れがあるため ≧ が必須だ。
